# BACKUP_RECOVERY.md

## Purpose

Define how Salikha Studio OS data is backed up, how recovery is executed, and how backups are verified. The system's books are only as trustworthy as its ability to be restored.

## Scope

- Backup strategy for the spreadsheet workbook (primary data store), Drive file tree, Script Properties, and Calendar.
- RPO (Recovery Point Objective) and RTO (Recovery Time Objective) targets.
- Disaster scenarios and runbook steps.
- Backup testing cadence.

Out of scope: GAS code versioning (that lives in the repo + deployment versions per `DEPLOYMENT_GUIDE.md`).

## Overview

Google Sheets is the single source of truth; losing or corrupting it is the only catastrophic data loss risk that matters. The strategy is **layered**:

1. Google-native versioning (daily point-in-time restore via Sheets version history).
2. Automated scheduled export of the workbook (App Script trigger → Drive backup folder).
3. Weekly export of the workbook to a **second location** (e.g., a separate Drive root or user-owned Drive).
4. Monthly cold backup (download to owner's personal storage) — offline.

RPO target: **≤ 24 hours** (daily backups; Google version history can go deeper). RTO target: **≤ 4 hours** for restore to a working web app.

## 1. What Needs Protecting

| Asset | Location | Risk |
|---|---|---|
| Workbook (all sheets) | Google Sheets | Accidental mass edit, script bug, share sabotage |
| Drive files (contracts, receipts, galleries) | Google Drive folder tree | Deletion, permission loss |
| Script Properties (secrets) | Script Properties | Loss of config; restored by hand |
| Calendar events | Google Calendar | Regenerated by mirror (low risk) |
| Apps Script code | Repo + deployment versions | Version history; push again |

## 2. Backup Strategy Layers

### Layer 1 — Native version history
Google Sheets keeps ~100 revisions (30 days extended by owner history). This is **not** a backup — it is a first line of defense. Enabled by default; do not disable.

### Layer 2 — Daily automated export (primary backup)
- Apps Script time-driven trigger (or GAS `onEdit`-independent job), runs **daily at 03:00 business time**.
- Job: copy the workbook via Drive API to `Backups/Salikha/<YYYY-MM-DD>_salikha.gsheet` (copy preserves sheets, not just values), plus export **CSV per sheet** for plain-value safety.
- The backup folder lives under the configured Drive root (`ROOT_DRIVE_FOLDER_ID`, see `docs/DEPLOYMENT_GUIDE.md §12a`) once the Files module exists; until then it may be a standalone folder.
- The copy must be **isolated**: only the service account/owner has access.
- Writes `Config.lastBackupAt` + an audit entry.

### Layer 3 — Weekly off-site export
- Trigger runs **Sundays 04:00**.
- Copies the latest daily backup to a second Drive folder owned by the business owner's personal account (e.g., shared folder `Salikha-Backups-Offsite`).

### Layer 4 — Monthly cold copy (manual)
- First of month: owner downloads the workbook + key folders to personal/external storage.
- Purpose: protection against workspace account-level loss.

---

## 3. Scheduled Jobs

| Job | Schedule | Scope | Failure handling |
|---|---|---|---|
| Daily backup | 03:00 daily | Workbook copy + CSV export | Retry at 05:00; alert owner via email |
| Weekly off-site | Sun 04:00 | Copy latest daily to off-site folder | Retry next hour; email alert |
| Backup verification | Sat 05:00 | Opens latest backup, computes row counts, validates checksum (row count + audit count) | Alert if mismatch |
| (Monthly cold copy) | Manual | Owner download | — |

All jobs are **idempotent** (no partial writes) and log to `AuditLogs`.

## 4. Retention

| Layer | Retention |
|---|---|
| Daily copies | 30 days (then auto-prune oldest) |
| Weekly off-site | 12 weeks |
| Monthly cold | 12 months (manual archive) |
| CSV exports | 30 days |

Pruning is a separate scheduled job (`BackupPruneJob`) that never deletes the newest 3 copies.

## 5. Restore Runbooks

### Scenario A — Corrupted/mistaken data (rows changed, app still works)
1. Identify the affected sheets/range in **version history** of the workbook.
2. Restore just that sheet's version to before the incident (30 min typical).
3. Verify with `system.ping` + a fixture report; log in `AuditLogs` (restore entry).

### Scenario B — Workbook deleted or unreadable
1. Open Drive backup folder → pick latest `salikha.gsheet` copy.
2. Copy it to production location; rename to production name.
3. Update `SPREADSHEET_ID` Script Property in the project (or re-bind).
4. Verify sequence counters (`Sequences`) are higher than any data row; else bump.
5. Confirm Web App works; run R1/R7 fixtures.
6. **Never restore into a live workbook with newer transactions** unless you intentionally roll back the clock — reconcile first.

### Scenario C — Full workspace account loss
1. Use monthly cold copy (Layer 4) as the source.
2. Create new workbook, import sheets, re-set Script Properties, re-deploy Web App (see `DEPLOYMENT_GUIDE.md`).
3. Accept data loss window up to 1 month if cold copies lapsed; restore backups first.

### Scenario D — Secrets/script lost
- Script Properties re-entered from `SECURITY_MODEL.md` secret inventory (keep a password-managed copy). Code re-pushed from repo (deployment version history intact).

## 6. Backup Testing

- **Weekly**: automated verification job (row counts, checksums, audit-count parity).
- **Monthly (first Saturday, manual)**: full **restore-in-anger** drill: restore latest backup into a scratch workbook, run G1–G11 global invariants from `TESTING_CHECKLIST.md`, then discard. Record result in this doc's run log.

```
## Restore Drill Log
2026-09-05  PASS — restored 2026-09-04 backup; invariants green (by: owner)
```

## 7. Disaster Scenarios

| Scenario | RPO | RTO | Runbook |
|---|---|---|---|
| Data corruption (rows) | ≤24h | 2h | A |
| Workbook deleted | ≤24h | 4h | B |
| Account lost | ≤30d (or per cold cadence) | 1d | C |
| Script config lost | — | 2h | D |

## 8. Responsibilities

- **Owner:** monthly cold copies, quarterly drill review, approving prune policies.
- **Automation (Sprint 8):** daily/weekly jobs; alerts go to Owner email.
- **Agent/Developer:** never runs restore drills against production; never bypasses the backup schedule in tests.

## 9. Future Expansion

- Multi-region snapshots via Google Cloud Storage (when SaaS).
- Point-in-time restore UI within the app.
- Backup integrity ledger (hash of each backup stored in `Config`).
